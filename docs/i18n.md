# Translator Guide — XMEye / Sofia Integration

This guide is the source of truth for adding or updating translations in
`custom_components/xmeye/translations/`. The rules in `AGENTS.md` are
authoritative; this document expands them with practical examples and per-locale
conventions.

## 1. Authoring principles

- **Contextual, not literal.** Do not translate word-by-word from English. Use
  the term a native HA user would actually expect to see, drawing on:
  - Home Assistant entity-name conventions (e.g., front door → "Front Door").
  - Security/CCTV industry terminology for that locale (e.g., CCTV firmware
    vendors in mainland China call it "人形检测" — that is what XMEye owners
    already see in their own app, and matching it makes the integration
    instantly familiar).
  - Local politeness (formal vs informal `you`, etc.).
- **Stable keys, fluid text.** JSON keys must stay identical to `en.json`. Only
  leaf string values change. Adding a new translatable string is fine; removing
  a key is a breaking change.
- **Placeholders are sacred.** `{channel}` and `{found}` are filled by HA at
  runtime — never hard-code numbers, never rename them. Their position around
  the noun follows the locale's convention (German puts the number after the
  noun, English puts it before — do not force English order).
- **Acronyms follow the locale.** `HDD` is universal in all current locales,
  but if a future entity adds an acronym, check what the local industry
  actually uses (e.g., DE often prefers spelled-out German terms in UI while ES
  UI often keeps English acronyms).

## 2. Key invariants

- Every leaf value in every `<locale>.json` MUST be present in `en.json` and
  vice versa — no extra keys, no missing keys.
- No leaf value may be `null`, an empty string, or accidentally a dict.
- Placeholder positions matter: if `en.json` has the placeholder, the locale
  must too. If `en.json` does NOT, the locale must NOT either.
- HDD `state` strings stay short and idiomatic (one word or short phrase).

## 3. Per-locale conventions

| Locale | Standard | Notable conventions |
|--------|----------|---------------------|

| `fr` | formal `vous` | `Détection de mouvement`, `Disque dur`, `Confidentialité` |
| `it` | formal `Lei` | `Rilevamento movimento / umano / volti`, `Disco rigido`, `Registrazione` |
| `pl` | formal `Pan/Pani` (UI convention is informal ok) | `Wykrywanie ruchu / osoby / twarzy`, `Dysk twardy`, `Prywatność` |
| `nl` | formal `u` | `Bewegingsdetectie`, `Persoonsdetectie`, `Gezichtsdetectie`, `Harde schijf` |

## 4. House rules

- **All locales at once.** A change to `strings.json` must propagate to
  `<locale>.json` for **every** locale in the same commit — never ship a
  partial update.
- **Native-speaker wins.** If a native speaker opens a PR improving
  wording, accept it. Do not revert to literal English. The keys in
  `strings.json` are the contract; the values in locale files are
  open for refinement.
- **`ru.json` attribution.** The Russian translation was contributed by
  community member `@ananyevgv` via
  [issue #28](https://github.com/equake/hass-xmeye/issues/28). Future
  improvements should credit them and reference the issue.

## 5. Validation

Run this from the project root to verify all locale files are key-identical
to `en.json` (no missing, no extra, no `null`, no empty values):

```bash
python3 - <<'EOF'
import json, pathlib
en = json.load(open("custom_components/xmeye/translations/en.json"))
def leaves(d, p=""):
    out = []
    for k, v in d.items():
        path = f"{p}.{k}" if p else k
        if isinstance(v, dict):
            out.extend(leaves(v, path))
        else:
            out.append((path, v))
    return out
en_keys = {p for p,_ in leaves(en)}
for f in sorted(pathlib.Path("custom_components/xmeye/translations").glob("*.json")):
    if f.name == "en.json": continue
    data = json.load(open(f))
    leafs = leaves(data)
    keys = {p for p,_ in leafs}
    miss = en_keys - keys
    extra = keys - en_keys
    bad = [(p,v) for p,v in leafs if not isinstance(v, str) or not v.strip()]
    print(f"{f.name}: missing={sorted(miss)} extra={sorted(extra)} bad={bad}")
EOF
```

Expected output: every line shows `missing=[] extra=[] bad=[]`.

## 6. Workflow when adding a new translatable string

1. Edit `strings.json` first — that is the canonical shape.
2. Mirror the change into `translations/en.json`.
3. Translate into every other locale file in the same commit.
4. Run the validator (section 5). It must return zero diff and zero bad values.
5. Run `ruff check custom_components/` (per `AGENTS.md`).

## 7. Workflow when adding a new locale

1. Create `translations/<locale>.json` from a copy of `en.json`.
2. Apply the conventions in section 3.
3. Update this guide with a new row in the per-locale table.
4. Open a PR; mention any native-speaker reviewers you tag.
